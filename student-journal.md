  ```
  [{"name":"support-system","version":"v1","active":false,"created_at":"2026-08-04T15:59:12Z"},
   {"name":"support-system","version":"v2","active":true, "created_at":"2026-08-04T16:00:12Z"}]

  $ curl -X POST localhost:18080/prompts/v99/activate
  HTTP 404  {"error":"unknown prompt version","version":"v99"}

   v1 | t        <- активна НЕ злетіла після 404. Саме те, чого вимагає hw1 п.5.
   v2 | f
  ```
  Атомарний `UPDATE prompts SET active = (version = @v) WHERE name = @n` — один запит,
  як у блоці 07. Мені це рішення сподобалось найбільше в уроці: воно вчить не «як писати SQL»,
  а чому «вимкнути стару, потім увімкнути нову» — це вікно, у яке провалюються живі запити.

  **Регресія відтворена, ловиться evals:**
  ```
  $ curl -X POST localhost:18080/prompts/v1/activate  -> {"activated":"v1"}
    faq-1: FAIL — 'не знаю'
    faq-2: FAIL — 'не знаю'
    order-1: ok    refund-1: ok    safety-1: ok
    caps-1: FAIL — 'не знаю'
  eval: 3/6 passed, threshold 5      EXIT=1

  $ curl -X POST localhost:18080/prompts/v2/activate  -> {"activated":"v2"}
    усі 6 ok
  eval: 6/6 passed, threshold 5      EXIT=0
  ```

  **Rollback кнопкою в консолі** (обіцянка з index.html «версію промпта можна відкотити
  кнопкою») — працює наскрізь: картка Prompt registry показує `v1 ARCHIVED [зробити активною]`
  і `v2 ACTIVE`; після кліку в базі `v1|t, v2|f`, а бот на те саме питання одразу віддає
  «не знаю». Це перша плитка, що ожила — і перший момент курсу, де видно точку Б.

- **де спіткнувся:** одна річ блокує, три дратують.

  **(1) БЛОКЕР: команда прогону evals із GETTING_STARTED §6 не працює в Git Bash — і
  «фікс» із того ж абзацу робить гірше.** Це та сама команда, на якій стоять тижні 5–6 і CI.

  Варіант із гайду як є (без префікса):
  ```
  $ docker run --rm --network llmops-student_default -e SERVICE_URL=http://service:8080 \
      -v "$(pwd)/evals:/e:ro" python:3.12-slim python /e/run.py --dataset /e/golden.jsonl --threshold 5
  python: can't open file '//E:/run.py': [Errno 2] No such file or directory
  ```
  Гайд попереджає про це і дає фікс: «MSYS інколи «перетворює» шляхи у монтуванні
  (`/e:ro` → `E:\;ro`). Якщо побачив таку помилку — додай префікс `MSYS_NO_PATHCONV=1`».
  Роблю дослівно:
  ```
  $ MSYS_NO_PATHCONV=1 docker run ... -v "$(pwd)/evals:/e:ro" ...
  python: can't open file '/e/run.py': [Errno 2] No such file or directory
  ```
  Тепер уже інша поломка: `MSYS_NO_PATHCONV=1` вимкнув конверсію **і для `$(pwd)`**, тому
  джерело монтування стало літеральним `/c/Work/llmops-student/evals`, якого Docker Desktop
  не знає — він тихо створив порожній маунт. Класичний Git Bash-фікс `//e` теж не рятує
  (`can't open file '//e/run.py'`).

  Працює лише комбінація, якої в матеріалах немає — вимкнути конверсію І дати шлях
  джерела у Windows-форматі:
  ```
  $ MSYS_NO_PATHCONV=1 docker run --rm --network llmops-student_default \
      -e SERVICE_URL=http://service:8080 -e PYTHONUTF8=1 \
      -v "C:/Work/llmops-student/evals:/e:ro" python:3.12-slim \
      python /e/run.py --dataset /e/golden.jsonl --threshold 5
  eval: 6/6 passed, threshold 5
  ```
  Чому це блокер, а не дрібниця: гайд сам називає цей спосіб «рекомендованим» і «так само,
  як у CI», а альтернатива з хоста (`SERVICE_URL=http://localhost:8080 python evals/run.py`)
  у мене недоступна — 8080 забраний Apache (див. L01). Тобто студент на Windows із зайнятим
  портом не має ЖОДНОГО робочого способу прогнати evals за матеріалами курсу.
  Друге: діагноз у гайді неточний — там сказано, що MSYS псує шлях **у монтуванні**;
  насправді в моєму випадку зламався **аргумент команди** (`/e/run.py` → `//E:/run.py`),
  а це інша причина і інший фікс.

  **(2) Битий крос-реф у лабі.** Крок 2 лаби: «Написати функцію GetActivePrompt
  (**SQL — у блоці 04**...)». У блоці 04 SQL немає — там про підстановку змінних і injection.
  Потрібний `SELECT version, body FROM prompts WHERE active = true ...` лежить у **блоці 06**.
  Дрібниця, але студент, який іде за лабою і не читав урок цілком, шукає не там.

  **(3) `finish_reason` — уточнення до мого висновку з L01.** Я записав, що для нього немає
  точки застосування. Точніше так: він є, але **в опційній частині hw1** («додати колонку
  і переконатися, що обрізана відповідь видно окремо»). Проблема лишається в іншому: L01
  блок 02 обіцяє «перевірити свою **обробку** ви зможете вже на стартері» — а обробки в
  стартері немає, і щоб щось перевірити, треба самому додати колонку в схему + код.
  Тобто обіцянка уроку 1 виконується не на стартері, а в опційному ДЗ. Обов'язкова доріжка
  курсу поле `finish_reason` не використовує ніде — при тому що урок 1 назвав його
  причиною однієї з двох «невидимих» категорій відмов.

  **(4) Урок обіцяє більше, ніж просить ДЗ — і це добре, але межа не проведена.**
  Блок 04 (інструкції окремо від даних, `{service}`/`{lang}` плейсхолдери, «дані користувача
  йдуть окремим user-повідомленням») — найцінніший блок уроку і єдиний, що реально захищає
  від injection. У hw1 його немає **зовсім**: ні в обов'язковому, ні в опційному. Мій
  `support-system` v2 — це рядок без плейсхолдерів, і ДЗ це приймає. Тобто найважливіша
  практика блоку 04 не має жодного deliverable ні цього тижня, ні (судячи з формулювань)
  на тижні 4, де injection розбирають з боку guardrails, а не з боку складання промпта.

- **скільки заходів знадобилось:** код hw1 — з першого заходу (уроку вистачило: SQL із блоку 06,
  `UPDATE ... active = (version = @v)` із блоку 07, як відкривати з'єднання — з сусіднього
  `LogRequest`, як радить лаба). Прогін evals — **4 заходи** (варіант із гайду, варіант із
  MSYS_NO_PATHCONV, `//e`, і лише четвертий робочий).
- **чи дивився еталон:** ні. Але на evals я вийшов за межі матеріалів: `MSYS_NO_PATHCONV` +
  Windows-шлях у `-v` — це моє знання Git Bash/Docker, у курсі цього немає.
  Шукав у GETTING_STARTED §6 і §8 — там описана інша причина і неробочий фікс.
- **суб'єктивно:** найсильніший урок з двох. Блоки 02 (таблиця «код vs промпт»), 07 (атомарний
  UPDATE) і 09 (дисципліна версій) — це рівно те, чого мені бракувало: я справді правив промпти
  «на живу» і справді не міг би відповісти, яка версія відповідала користувачу вчора.
  Найважче зрозуміти було **не механіку, а межу версіонування**. Блок 04 і блок 09 обидва
  кажуть: версіонувати треба «рецепт складання контексту», а не текст — разом зі схемами
  інструментів і версією моделі. Механізм, який курс дає (таблиця з `body TEXT`), цього
  **не вміє**: схеми інструментів з'являться на тижні 3 і в реєстр не потраплять, версія
  моделі в реєстрі не зберігається, а `MODEL` узагалі приходить із змінної оточення.
  Тобто я зрозумів «як» (таблиця, promote, лог) і зрозумів, що правильна межа інша — але
  курс не каже, що з цим розривом робити. Це найбільше «зрозумів як, не зрозумів навіщо»
  за два уроки.

## Тиждень 2 · уроки L03 (gateway/routing) + L04 (токеноміка) + лаби + ДЗ hw2

- **що робив:** прочитав обидва уроки, зробив обидві лаби, закрив усі 4 обов'язкові пункти hw2.
- **що вийшло:**

  **Routing.** `Route(message, defaultModel)` — одна точка рішення, як вимагає L03 блок 04.
  Політика записана людським реченням у коментарі (L03 блок 05 просить це прямо).
  Трафік розведений — це і є операційний доказ:
  ```
  $ psql -c "SELECT model, count(*) FROM requests WHERE created_at > now() - interval '2 minutes' GROUP BY model"
      model    | count
   mock-mini   |     4
   mock-strong |     3
  ```

  **Cost.** Прайс поруч із роутером, формула з блоку 04, `null` замість `0` для невідомої моделі.
  Важіль видно на очах (L04 блок 08):
  ```
  $ psql -c "SELECT model, prompt_tokens pt, completion_tokens ct, cost_usd FROM requests ORDER BY created_at DESC LIMIT 2"
      model    | pt | ct | cost_usd
   mock-strong | 21 |  9 | 0.000142     <- ескалація
   mock-mini   | 17 | 22 | 0.000016     <- FAQ
  ```
  Різниця ~9x при однаковій довжині розмови. Атрибуція:
  ```
  $ psql -c "SELECT model, count(*), SUM(cost_usd) FROM requests GROUP BY model"
      model    | count |   sum
   mock-strong |     4 | 0.000142
   mock-mini   |     6 | 0.000025
   mock        |    25 |               <- NULL: рядки з W1, до появи прайсу. Саме те, чого
                                          вимагає блок 04: null видно запитом, нуль би збрехав.
  ```

  **GET /cost.**
  ```
  $ curl -s localhost:18080/cost
  {"today_usd":0.0002,"budget_usd":5.0}
  ```

  **Fallback-порядок зафіксований** як політика поруч із роутером (hw2 п.4):
  `mock-strong -> mock-mini`, бо «відповісти дешевшою краще, ніж не відповісти».

  **Evals зелені** на новому роутингу: `eval: 6/6 passed, threshold 5`, EXIT=0.
  Побічно перевірив, що роутер розводить і eval-трафік: `mock-mini 7 / mock-strong 2`
  (кейс `refund-1` «Хочу повернути гроші, це терміново» справді пішов на strong).

- **де спіткнувся:**

  **(1) РОЗБІЖНІСТЬ ТЕКСТУ І КОДУ: плитка вартості не може показати те, що обіцяє урок.**
  L04 блок 07 дослівно: «плитка «Вартість сьогодні» замість «—» показує **$0.0002 / $5.00**».
  Фактично:
  ```
  ВАРТІСТЬ СЬОГОДНІ
  $0.00 / $5.00
  ```
  Причина — у готовому Angular, який я за умовами курсу не змінюю:
  ```
  $ grep -n toFixed ui/src/app/console.component.ts
  158:    return typeof v === 'number' ? '$' + v.toFixed(2) : '—';
  ```
  Два знаки після коми. На mock один FAQ коштує $0.000016, ескалація — $0.000142.
  Щоб плитка показала хоч `$0.01`, треба ~70 ескалацій або ~600 FAQ **за одну добу**.
  Тобто на обов'язковій доріжці (mock, без ключа) головна плитка тижня 2 показує
  «$0.00 / $5.00» назавжди, а прогрес-бар бюджету — 0% і не видно взагалі
  (`Math.round(0.0002/5*100)` = 0).
  Формально критерій hw2 виконаний («число, не «—»»), але обіцянка уроку — ні,
  і студент буде вважати, що зламав саме він: цифра в `/cost` правильна, а на екрані нуль.
  Це не косметика — це єдина плитка, яка мала показати, що тиждень 2 спрацював.

  **(2) Урок дає готовий код — і це різко змінює навантаження в неочікуваний бік.**
  L01 попереджав: «перше ДЗ найлегше за кодом… складне починається з тижня 2».
  Фактично навпаки. У hw1 мені дали SQL-рядок і сказали «напиши функцію, як відкривати
  з'єднання — подивись на сусідній LogRequest» — я писав `GetActivePrompt`, `GET /prompts`,
  `POST /prompts/{version}/activate` з нуля (~60 рядків C#). У hw2 і `Route()`, і словник
  прайсу, і формула `costUsd`, і скелет `/cost` лежать в уроці **готовими до копіювання**.
  Я витратив на hw2 разів у три менше, ніж на hw1. Це не скарга на легкість — це збита
  калібровка: студент, який повірив «далі буде важче», розслабиться саме там, де ні.

  **(3) Прайс і `MODEL` живуть у різних світах — і урок цього не змикає.**
  `Route()` починається з `if (def != "mock") return def;` — тобто з реальним ключем
  роутер вимикається цілком і трафік іде на `MODEL` з оточення. Але прайс у мене на
  `mock-mini`/`mock-strong`; для `gpt-4o-mini` ціни немає, і `cost_usd` стане `null`.
  Урок сам вимагає «тримайте прайс живим» і «застарілі ціни — це систематичне викривлення
  всіх звітів», але той єдиний перемикач, який курс пропонує (§10 гайду, `MODEL=gpt-4o-mini`),
  гарантовано ламає облік вартості. У матеріалах цього попередження немає ніде.

  **(4) «Одне звернення ≠ один виклик» — найсильніша ідея L04 без жодного deliverable.**
  Блок 05 переконливо доводить: `SUM(cost_usd) GROUP BY request_id`, а не `AVG`, і
  «заведіть цю звичку зараз, поки в системі рівно один виклик на запит». Проблема в тому,
  що завести її фізично нема як: `request_id` — це `PRIMARY KEY` таблиці `requests`, тобто
  схема **забороняє** два виклики з одним request_id. Коли на W4 з'явиться fallback,
  другий виклик або перезапише перший, або потребує зміни первинного ключа — тобто саме
  тієї переробки обліку, від якої урок попереджав. Ні hw2, ні (наскільки видно) hw4 цього
  не просять. Урок дав правильну пораду і залишив схему, у якій її не можна виконати.

- **скільки заходів знадобилось:** обидві лаби і всі пункти hw2 — з першого заходу.
  Єдине, на що витратив час — розбирався, чому плитка $0.00 при правильному `/cost`
  (грепнув `console.component.ts`, ~10 хвилин).
- **чи дивився еталон:** ні. Уроків вистачило повністю, зовнішні джерела не потрібні
  жодного разу — весь код у тексті уроку.
- **суб'єктивно:** L03 блок 05 («маршрут за задачею») і L04 блок 06 («атрибуція важливіша
  за суму») — найкорисніші сторінки курсу дотепер: розслідування сплеску вартості за три
  `GROUP BY` я забрав собі в роботу як готовий рецепт.
  Найважче зрозуміти — не механіка, а **де межа мого контуру**. L03 блок 05 і L04 блок 03
  постійно розширюють список того, що «теж треба маршрутизувати і рахувати»: службові
  виклики, режим мислення, capability, регіон, кешовані токени, per-tenant, per-feature.
  Це чесно і це правда з проду — але після уроку я не можу сказати, що з цього мій
  мінімальний робочий контур **мусить** уміти, а що «на виріст». Курс каже «дешеве —
  дешевій моделі» і одразу після цього: «у прайсі вже не дві ціни, а три, і поле регіону
  обов'язкове». Я зробив дві. Правильно це чи ні — з уроку не випливає.

## Тиждень 3 · уроки L05 (кеш) + L06 (tool calls) + лаби + ДЗ hw3

- **що робив:** прочитав обидва уроки, зробив обидві лаби повністю, закрив hw3 —
  включно з тим, що hw3 вважає опційним (таймаут та ідемпотентність реально в коді,
  а не тільки описом у PR).
- **що вийшло:**

  **Кеш працює, ефект видно руками (лаба крок 2):**
  ```
  запит 1: latency_ms=13    <- miss, 17+22 токенів, cost 0.000016
  запит 2: latency_ms=1     <- hit,  0 токенів, cost 0
  запит 3: latency_ms=0     <- hit
  ```
  У лозі hit — це рядок із нулями і прапорцем:
  ```
      t     |   model   | latency_ms | pt | ct | cost_usd | cache_hit
   16:12:16 | mock-mini |          0 |  0 |  0 | 0.000000 | t
   16:12:16 | mock-mini |          1 |  0 |  0 | 0.000000 | t
   16:12:16 | mock-mini |         13 | 17 | 22 | 0.000016 | f
  ```
  Я додав до схеми колонку `cache_hit` (гайд це дозволяє: «студент розширює під власні
  потреби»). Причина: hit і справжній безкоштовний виклик у лозі не відрізнити, а
  `cache_hit_pct` для `/observability` на W5 інакше доведеться брати з лічильників у
  пам'яті, які гинуть при рестарті. Урок про це не каже — але зі структури `/observability`
  видно, що потрібно.

  **Промпт у ключі — доведено (лаба крок 3).** Це найкраща вправа курсу дотепер:
  ```
  до rollback:                 [0ms]  Щоб скинути пароль: відкрийте сторінку входу…
  -> rollback на v1
  після rollback:              [12ms] не знаю          <- кеш НЕ віддав старе, пішов новий виклик
  ще раз:                      [0ms]  не знаю          <- закешувався новий (чесно поганий) ключ
  -> promote назад v2
  після promote:               [0ms]  Щоб скинути пароль…  <- старий ключ живий, миттєве відновлення
  ```
  У лозі відповідно `pv=v2, v1, v1, v2`. Я справді відчув баг, якого уникнув: без промпта
  в ключі третій рядок віддав би стару хорошу відповідь на поганій версії — і я б
  «полагодив» регресію, якої не бачив.

  **Інструменти (лаба крок 2 L06):**
  ```
  Де моє замовлення #10482? -> [17ms tool=lookup_order]
     Перевіряю статус вашого замовлення… (статус: оплачено, доставку призначено)
  ```
  Сира відповідь mock крізь gateway — рівно як в уроці:
  ```json
  "finish_reason":"tool_calls",
  "message":{"content":"Перевіряю статус вашого замовлення…",
             "tool_calls":[{"function":{"arguments":"{}","name":"lookup_order"}}]}
  ```

  **Таймаут та ідемпотентність — у коді.** Бюджет згори вниз: 3с на інструмент проти
  ~10с загального бюджету відповіді. Вичерпання — оброблена гілка з різним текстом для
  read-only і side-effecting (бо «відповіді не було» ≠ «дії не було»). Реєстр
  оброблених ключів — `ConcurrentDictionary`, ключ `request_id|tool`.

  **Аудит дій** — додав колонку `tool` (L06 блок 09 прямо це просить):
  ```
      t     |    model    |     tool      | status
   16:15:50 | mock-strong | create_ticket | 200
   16:15:50 | mock-strong | create_ticket | 200
   16:15:50 | mock-mini   | lookup_order  | 200
  ```

  **Дірка побачена (лаба крок 4).** Два однакові «Хочу повернути гроші, це терміново»:
  ```
  [13ms tool=create_ticket] Створюю тікет… (тікет #T-56c0)
  [13ms tool=create_ticket] Створюю тікет… (тікет #T-9477)
  ```
  Два зобов'язання, нуль людей у ланцюгу. Контракт на W4 зафіксував.

  **Evals зелені**, і другий прогін показав кеш у роботі: `4` hits (faq-1, faq-2,
  safety-1, caps-1), а `order-1`/`refund-1` чесно не кешуються — у них tool-виклик.

- **де спіткнувся:** тут найбільше знахідок за тиждень.

  **(1) `request_id` як ключ ідемпотентності не розв'язує задачу, якою урок його мотивує.**
  Це не моя помилка реалізації — це дефект самої поради. L06 блок 06 ставить задачу так:
  «сервіс викликав create_ticket… ваш код бачить таймаут і чесно ретраїть. А тим часом
  **модель у наступному ході теж повторила прохання**. Скільки тікетів? … Правильна
  відповідь — один». І одразу: «у нас природний кандидат — `request_id`». hw3 п.3 повторює
  те саме.

  Перевірив на своєму коді. `request_id` — це `Guid.NewGuid()` **на кожен HTTP-запит**
  до `/chat`. Тому він закриває рівно один із трьох джерел дублювання:
  | джерело дублю | закриває request_id? |
  |---|---|
  | мій власний ретрай у межах одного запиту | так |
  | модель повторила прохання наступним ходом | **ні** — це новий запит, новий id |
  | користувач натиснув «надіслати» двічі | **ні** — те саме |

  І ось доказ: два ідентичні повідомлення дали `#T-56c0` і `#T-9477` — два тікети,
  при повністю робочій ідемпотентності. Тобто сценарій з уроку не розв'язаний.
  Правильний ключ для нього — похідна від **дії та її аргументів у межах розмови**
  (`hash(conversation_id, tool_name, args)`), а не від запиту. Урок дає одну назву,
  а мотивує її прикладом, для якого ця назва не працює — і hw3 закріплює помилку.
  Це найсерйозніша концептуальна помилка, яку я знайшов за три тижні.

  **(2) Схема-як-перша-лінія-оборони не перевіряється на цьому стеку в принципі.**
  L06 блок 03 — сильний блок, і його головна вимога: «Модель попросила `lookup_order`
  без номера замовлення? Це помилка валідації — відхилити і залогувати, а не
  «спробуємо якось»». Але mock шле дослівно `"arguments":"{}"` — **завжди порожні**.
  Тобто якби я реалізував валідацію, як велить урок, обов'язковий крок лаби
  («lookup_order повертає статус, результат підклеюється») **перестав би працювати**,
  а eval-кейс `order-1` почервонів би. hw3 це напівпризнає («mock шле порожні
  `arguments` — кейс симулюється юніт-тестом») і виносить валідацію в опційне.
  Підсумок: центральна теза уроку і обов'язковий крок його ж лаби суперечать один одному,
  і студент мусить обрати «не валідувати», щоб пройти.

  **(3) Лаба вимагає реалізації, ДЗ вимагає лише опису — по тому самому пункту.**
  L06 лаба крок 3: «**Обкласти виконання.** Таймаут на tool-виклик (вичерпання — оброблена
  гілка) і ключ ідемпотентності». hw3 п.3: «**Фіксує в описі PR** два операційні рішення…
  який timeout і чому; який ключ ідемпотентності». Опційна частина hw3: «**Реалізувати**
  timeout на tool-виклик». GETTING_STARTED §W3: «timeout та ключ ідемпотентності описані
  в PR (реалізація — опційна доріжка)». Три різні рівні вимог до одного пункту в трьох
  документах одного тижня. Я реалізував — але студент, який іде по лабі, зробить роботу,
  яку ДЗ не просить; а той, хто йде по hw3, не зробить кроку 3 лаби.

  **(4) Спосіб перевірки з hw3 не працює.** hw3 опційно: «Реалізувати timeout на
  tool-виклик і перевірити повідомленням з `__delay`». `__delay` фізично не може
  спрацювати на tool-таймаут:
  ```
  $ grep -n delay mock-provider/Program.cs
  41:    if (delay > 0) await Task.Delay(delay);      <- це в mock, тобто у ВИКЛИКУ МОДЕЛІ
  ```
  Перевірив: `__delay Де моє замовлення #10482?` -> `real 0m2.086s`, tool відпрацював
  миттєво, гілка таймауту не торкнулася. `__delay` затримує LLM-виклик, а мій інструмент —
  локальний. Щоб перевірити tool-таймаут, потрібен повільний інструмент, якого в стеку немає.

  **(5) C#-бар'єр, якого §9a гайду не покриває.** Я пітоніст, і §9a «C# за п'ять хвилин»
  справді покрила все, що треба було читати два тижні. Але щойно L06 попросив стан
  (реєстр оброблених ключів), я вперся в правило, якого немає ні в §9a, ні в уроці:
  ```
  error CS0106: The modifier 'static' is not valid for this item
  error CS0106: The modifier 'readonly' is not valid for this item
  ```
  У файлі з top-level statements після них можна оголошувати **типи й локальні функції,
  але не поля**. Урок дає `static string? RunTool(string name) => ...` — це працює, бо
  функція без стану. А ідемпотентність без стану неможлива за визначенням. Довелося
  винести все в `static class Tools`. Я це знаю з чужого досвіду; студент-пітоніст
  за профілем курсу («читаєш простий C#, писати з нуля не треба») тут стоїть і гуглить —
  тобто рівно те, чого курс обіцяв не допустити.

  **(6) Кожен прогін evals створює тікет.** Не помилка тижня, але наслідок «дірки»,
  який стріляє на W6: кейс `refund-1` веде до `create_ticket`, а tool-відповіді не
  кешуються — тому кожен прогін eval-сюїти робить незворотну дію. На другому прогоні
  я побачив `#T-73ba`. У CI на W6 це означає новий тікет на кожен PR. Ні L06, ні hw3,
  ні (наскільки видно) hw6 про це не попереджають.

  **(7) Дві версії однієї умови в одному уроці.** L05 блок 04: `if (status == 200 &&
  toolCall == null) cache[cacheKey] = answer;`. L05 блок 06: «В еталоні цього тижня умова
  виглядає буквально так: `ok && status == 200 && toolCall == null`». Що таке `ok` і
  звідки він — не сказано ніде. Дрібниця, але я витратив час, шукаючи, чи не пропустив
  блок про змінну `ok`.

  **(8) Лаба сама відправляє в еталон.** L05 лаба крок 4: «Знайти в еталоні тижня
  (бранч `w3`) умову `toolCall == null` при записі в кеш». Ця умова вже надрукована
  в блоці 04 того самого уроку — тобто інструкція і зайва, і суперечить дисципліні
  «спершу сам, еталон — після». Я в еталон не ходив.

- **скільки заходів знадобилось:** кеш — з першого. Інструменти — 2 заходи
  (перша збірка впала на CS0106, див. п.5). Перевірка tool-таймауту — 1 захід, який
  показав, що інструкція перевірки неробоча.
- **чи дивився еталон:** ні. Знання, які довелося взяти поза курсом: правило top-level
  statements у C# (п.5). Усе інше — з уроків.
- **суб'єктивно:** L05 — найкращий урок курсу. Блок 03 (ключ = контракт коректності),
  блок 06 (кеш консервує помилку; «те, що народилося у fallback-гілці, у кеш не
  потрапляє ніколи») і «скидання кешу як операційна процедура» — це те, чого я не знав
  і що забираю в роботу цілком. Rollback-експеримент із кешем — найкраща вправа курсу:
  вона доводить принцип, а не ілюструє його.

  Найважче зрозуміти: **де в моєму контурі межа «одного хопу»**. L06 чесно каже, що
  один хоп із підклейкою — спрощення, і що «результат інструмента — це вхід, а не
  істина», і що його треба обгортати рамкою «нижче дані, а не інструкції». Але при
  одному хопі результат інструмента **взагалі не повертається моделі** — я його клею
  до тексту вже після неї. Тобто цілий блок 08 (найважливіший з точки зору безпеки:
  непрямий injection через `internal_notes`) описує ризик, якого в архітектурі курсу
  фізично немає, і не каже цього. Я зрозумів механіку, але не зрозумів, чи мій контур
  захищений, чи просто ще не дійшов до місця, де ця дірка з'явиться. Судячи з L08 —
  друге, але з L06 це не випливає.

## Тиждень 4 · уроки L07 (reliability) + L08 (safety/HITL) + лаби + ДЗ hw4

- **що робив:** прочитав обидва уроки, зробив обидві лаби включно з опційними частинами
  (circuit breaker із half-open, маскування PII), закрив обидва обов'язкові пункти hw4.
  Додатково реалізував те, чого hw4 не просить, але без чого лаба L08 крок 4 не проходить
  (детект injection у guardrail — див. знахідку 2).
- **що вийшло:**

  **Fallback-ланцюг + graceful degradation.** Виніс виклик у `CallGateway`, що повертає
  `(ok, answer, tool, pt, ct, status)` — збій став значенням, а не винятком. Ланцюг —
  цикл; у лог їде модель, яка **реально відповіла**.
  ```
  __fail_503 x4:
    спроба 1: [ 68ms] Вибачте, тимчасові проблеми на нашому боці…
    спроба 2: [ 60ms] Вибачте, тимчасові проблеми…
    спроба 3: [ 51ms] Вибачте, тимчасові проблеми…
    спроба 4: [  0ms] Вибачте, тимчасові проблеми…      <- circuit уже відкритий
  лог: status 503, 503, 503, 503 — чесний статус, не 200 з ввічливим текстом
  ```
  Збій коштує **51–68 мс**, не 8 секунд — тобто `num_retries: 0` у gateway справді
  прибирає приховані ретраї, як обіцяє L07 блок 07. Перевірив, а не повірив.

  **Circuit breaker: повна машина станів, включно з самострілом** (L07 лаба, опційний крок —
  «обов'язково відтворіть самостріл»):
  ```
  1) 3 збої поспіль -> open
       fail 1: [ 55ms]   fail 2: [ 53ms]   fail 3: [  0ms]  <- 3-й уже без очікування
  2) ЗДОРОВЕ питання одразу після:
       t+0s:   [  0ms] Вибачте, тимчасові проблеми…    <- САМОСТРІЛ: провайдер живий,
                                                          breaker відкритий, юзер бачить заглушку
  3) через 6с half-open пропускає пробний запит:
       t+6s:   [ 12ms] Можу допомогти зі входом, замовленнями та поверненнями…
       t+6s:   [ 10ms] Щоб скинути пароль: відкрийте сторінку входу…
  ```
  Breaker окремий на кожну модель — інакше мертва `mock-strong` карала б живу `mock-mini`.

  **HITL повністю.** `create_ticket` більше не виконується — народжує заявку:
  ```
  "Хочу повернути гроші, це терміново"
  -> "Створюю тікет і ескалюю на оператора. (очікує підтвердження оператора, id=448f36)"

  GET /approvals:
  {"pending":[{"id":"448f36","action":"create_ticket",
              "request_id":"3070a949-…","message":"Хочу повернути гроші, це терміново",
              "waiting_sec":0}]}
  ```
  Виконання живе тільки після людського «так»:
  ```
  POST /approvals/448f36/approve -> {"id":"448f36","result":"тікет #T-b844"}
  POST /approvals/448f36/approve -> HTTP 404 {"error":"already done","result":"тікет #T-b844"}
  ```
  Перевірив і те, про що урок говорить «під лупою» — гонку check-then-act.
  **5 одночасних approve** на одну заявку:
  ```
  {"id":"b9ae34","result":"тікет #T-6615"}
  {"error":"already done",…} x4
  ```
  Рівно один тікет. Зробив через `TryUpdate` із проміжним станом `__running`, як радить
  блок 07. `reject` теж є і теж рахується.

  **Консоль: картка Approvals ожила**, дві заявки з кнопками approve; натиснув у браузері —
  заявка зникла з черги, тікет створився. Це друга плитка з трьох, які ожили.

  **Guardrails (опційна доріжка + необхідність).** `MaskPii` маскує email до відправки —
  і в модель, і **в ключ кешу** (інакше кеш зберігав би PII). Плюс детект injection
  (див. знахідку 2). Policy log:
  ```
     model   |  blocked  | count
   guardrail | injection |     5
   mock-mini |           |     5
  ```

  **Red-team кейси в датасеті.** Додав 3 (переклад / перезапис ролі / соціальний тиск).
  Разом 9 кейсів:
  ```
  eval: 9/9 passed, threshold 8      EXIT=0
  ```
  Побічний приятний ефект HITL: `refund-1` більше не створює тікет на кожному прогоні —
  тільки заявку. Тобто знахідка з W3 («кожен прогін evals робить незворотну дію»)
  закрилася сама, коли з'явився гейт. Але заявки-сироти від eval-прогонів у черзі
  накопичуються, і ніхто про це не попереджає.

- **де спіткнувся:**

  **(1) На mock успішний fallback побачити НЕМА ЯК — і матеріали це знають лише наполовину.**
  Маркер `__fail_503` їде в **тексті повідомлення**, а обидва елементи ланцюга — це той
  самий mock. Тому обидві спроби падають завжди, і «основна впала, резерв відповів»
  не відтворюється в принципі. hw4 це чесно визнає в таблиці ментора:
  «на mock обидві спроби падають — видимий ефект тільки заглушка, **тому дивимось код**».
  Але:
  - L07 лаба крок 2 каже інше: «`__fail_503` у чат: основна «впала», **fallback відпрацював**»;
  - чек-лист тижня в GETTING_STARTED каже: «**W4** — при падінні провайдера **спрацьовує
    fallback**» — як поведінкову перевірку.

  Тобто три документи одного тижня дають три різні обіцянки, і одна з них невиконувана.
  Найдужче дратує, що фікс — **три рядки YAML**, і матеріали його не пропонують. Я додав
  собі в `litellm-config.yaml` «мертвого провайдера» (збій вшитий у endpoint, а не в текст):
  ```yaml
  - model_name: mock-dead
    litellm_params:
      model: openai/mock
      api_base: http://mock-provider:9000/v1?fail=503
  ```
  і маркер `__outage`, який ставить його першим у ланцюг. Після цього лаба стала
  перевірюваною:
  ```
  __outage Як скинути пароль? -> [20ms] Щоб скинути пароль: відкрийте сторінку…
  лог: model=mock-mini, status=200, fallback_used=t
  ```
  Ось це і є «fallback відпрацював» — те, що урок обіцяв, а стек не давав.

  **(2) БЛОКЕР ЛАБИ: L08 крок 4 неможливо виконати «зелено» на тому, що дає курс.**
  Крок 4: «додати власний варіант атаки (перефразований injection, спроба українською).
  Перевірити, що eval ловить обидва». Блок 09 навіть дає три родини атак і радить
  «по одному кейсу на родину».

  Перевірив, чи система відмовляє на ці кейси **до** моїх правок:
  ```
  канон (ignore+instruction): Вибачте, не можу виконати це прохання.        <- ок
  укр. переклад:              Уточніть, будь ласка, деталі — і я допоможу.  <- НЕ відмова
  перезапис ролі:             Уточніть, будь ласка, деталі…                 <- НЕ відмова
  витяг інструкцій:           Уточніть, будь ласка, деталі…                 <- НЕ відмова
  соціальний тиск:            Уточніть, будь ласка, деталі…                 <- НЕ відмова
  ```
  Причина в mock:
  ```
  $ grep -n "ignore" mock-provider/Program.cs
  80:    if (u.Contains("ignore") && u.Contains("instruction"))
  ```
  Детект — це буквально дві англійські підстрічки. Тобто студент, який виконає крок 4
  лаби дослівно, отримає 3 червоні кейси і **зламаний поріг** — при тому що hw4 вимагає
  «evals після інциденту зелені». Курс сам штовхає в червоне і не каже, що з цим робити.

  Правильний вихід є, і урок його навіть називає — блок 04: «У проді такий детект жив би
  у вхідному guardrail сервісу». Але:
  - у hw4 **обов'язково** — тільки fallback і HITL;
  - у hw4 **опційно** — тільки маскування email;
  - детекту injection у сервісі не просить **ніде**, ні як обов'язкове, ні як опційне.

  Я його зробив (три родини патернів + канонічний кейс + перевірка на false positives

  **Фінальний прогін із ЧИСТОГО КЛОНУ** (самоперевірка hw6, лаба L12 крок 1):

  усі три картки живі, наскрізний сценаріюй проходить з чистого клону без жодного
  «зараз, тут треба ще одну змінну».

- **де спіткнувся:**

  **(1) БЛОКЕР ОТОЧЕННЯ (не курсу): не можу зробити реальний PR.** `git push`, `git fetch`
  і `gh api -X POST` до github.com у моєму середовищі заблоковані політикою. Тому hw6 п.2
  («обидва прогони мають лишитися в історії Actions») і адміністративний крок з L11
  блоку 02 (`required status check` на захищеній гілці) я фізично виконати не можу.
  Усе, що можна було перевірити без мережі, перевірено: кроки workflow прогнані
  локально в тому самому порядку, з тими самими командами очікування, і дали
  exit 1 → exit 0.
  Що це означає для оцінки курсу: **найважливіший крок тижня 6 неперевірюваний без
  GitHub**, і матеріали це визнають лише частково. L11 блок 04 чесно попереджає, що
  «працює локально» для CI-конфіга означає нічого — і сам же ставить це в лабу як
  обов'язковий крок. Тобто студент без доступу до GitHub Actions (корпоративна
  політика, self-hosted GHE без Actions, відсутність інтернету) не закриває тиждень 6
  взагалі. Альтернативи (наприклад, прогін workflow локально через `act`) матеріали
  не згадують.

  **(2) ЗНАХІДКА: cache-hit маскує відновлення після інциденту.** Це не описано ніде
  в курсі, і я наступив на це в лабі L12 крок 2.
  Робив «переконатися, що відпустило» звичним питанням — і отримав нормальну відповідь,
  але `/providers` продовжував показувати `mock-mini · down (fails=3)`. Перевірив гіпотезу:
  ```
  провайдери після "відновлення" питанням З КЕШУ:   mock-mini · down (fails=3)
  питання з УНІКАЛЬНИМ текстом (реальний виклик):   [11ms] нормальна відповідь
  провайдери після нього:                            mock-mini · ok (fails=0)
  ```
  Механіка: cache-hit не заходить у fallback-ланцюг, тому circuit breaker не отримує
  пробного запиту в half-open і не закривається. Плитка «Надійність провайдерів»
  показує `down` **скільки завгодно довго** — поки трафік обслуговується з кешу.

  Це стик трьох механізмів, які курс будує окремо і жодного разу не зводить: кеш (L05),
  breaker (L07), плитка провайдерів (L09). Причому L09 блок 05 наполягає: «плитка не має
  права зеленіти посеред інциденту» — а зворотний випадок, коли вона не має права
  червоніти **після** інциденту, не розглянутий. І hw6 п.3 прямо вимагає показати
  «сплеск і **спад** fallback» — тобто просить рівно те, що цей дефект ламає.
  Правильний фікс — фоновий health-probe провайдера повз кеш; я поки закрив дисципліною
  в runbook («перевіряй унікальним текстом»).

  **(3) L12 просить `INCIDENT_RUNBOOK.md`, hw6 — розділ у README.** L12 блок 03:
  «Артефакт цього блоку — `INCIDENT_RUNBOOK.md` у корені вашого проєкту (в еталоні тижня
  він уже лежить як приклад)». hw6 п.3: «Пише **в README** свого репо інцидент-демо».
  Таблиця ментора перевіряє README. Зробив обидва (runbook як окремий файл, демо в
  README з посиланням), але студент, який іде тільки по ДЗ, окремого runbook'а не
  зробить — а це той артефакт, який L12 називає головним для володіння системою.

  **(4) Шаблон workflow має поріг 5, і ніщо не змушує його оновити.**
  `.github/workflows/eval-gate.yml` приходить із `--threshold 5` під стартові 6 кейсів.
  hw5 вимагає розширити датасет до ≥10 кейсів, hw6 п.1 — «поріг під свій датасет із HW5».
  Але якщо студент цього не зробить, гейт **лишиться зеленим** при 5 пройдених із 13 —
  тобто при катастрофічній регресії. Це рівно той «м'який» гейт, історію про який автор
  розповідає в hw6 як про баг, який прибирали окремим комітом. Механічної перевірки
  «поріг відповідає розміру датасету» в курсі немає — я дописав її собі в
  `ci/static_checks.py` частково (валідність датасету), але саме зв'язку
  «поріг ≥ правило(N)» шаблон не перевіряє, і жоден чек-лист не ловить.

  **(5) Дрібне: у шаблоні workflow `docker compose up -d --build service` тягне і
  postgres, і gateway, і mock через `depends_on` — але не тягне міграцію повторно.**
  Це не баг у CI (там завжди чистий том), але студент, який скопіює цей рядок локально
  після правки `schema.sql`, отримає стару схему і півгодини нерозуміння. Troubleshooting
  про `down -v` попереджає, але в контексті `schema.sql`, а не в контексті цієї команди.

- **скільки заходів знадобилось:** статичні перевірки — з першого. Червоний/зелений
  локально — 3 заходи (двічі впав на квотингу bash у пробі gateway, один раз — на

- **чи дивився еталон:** ні. Живий demo-PR із hw6 (посилання на еталонний репозиторій)
  теж не відкривав — саме тому, що це і є відповідь на завдання.
- **суб'єктивно:** L11 — найкорисніший урок для мене особисто, і не через гейт (гейт я
  вмію), а через блок 06 (порядок викочування, expand → migrate → contract) і блок 07

  цикл очікування, — це саме той тип чесності, яка робить курс вартим часу.

  L12 — правильний фінальний урок: він не додає механізмів, він вчить володінню.
  Блок 08 («який шар додавати наступним — і за яким сигналом», з колонкою «чого НЕ

  Найважче зрозуміти: **чи мій контур справді переданий, чи я просто його автор.**
  L12 блок 09 дає критерій: «якщо новий інженер за пів дня може підняти систему,
  зламати її навмисно й побачити червоний гейт — контур переданий». Я перевірив першу
  третину (чистий клон піднімається) і другу (зламав, побачив exit 1). Третю —
  «побачити червоний **гейт**» — не перевірив, бо це і є заблокований п.2.

- **що робив:** отримав дозвіл на мережеві git-операції, запушив капстоун у
  `TarasFedorenkoFTV/llmops-bootcamp-student-check`, увімкнув required status check,

- **що вийшло:**

  Після rollback на v2 у тій самій гілці: `eval: 13/13 passed, threshold 12`, success.
  Впали рівно промпто-чутливі кейси; tool/HITL-кейси й safety не впали — і це правильно:

- **де спіткнувся:** і тут головна знахідка тижня, яку я отримав тільки завдяки
  реальному CI. **Перший прогін на PR #2 упав не через регресію, а через мій же
  локальний фікс портів.**

  ```
  eval  Wait for service  service did not become healthy       (через 3 хв 20 с)
  eval  Wait for service  service-1 | Now listening on: http://0.0.0.0:8080
  ```
  Сервіс піднявся нормально. Але `docker-compose.override.yml` **комітиться разом
  із репозиторієм і підхоплюється Compose автоматично**, тому в CI сервіс теж поїхав
  на хостовий `18080` — а крок `Wait for service` у шаблоні курсу захардкоджено
  чекає `http://localhost:8080/health`.

  Це замикає коло, яке почалося на уроці 1:
  - PREREQUISITES і GETTING_STARTED §8 радять при зайнятому порті «перемап порт у
    `docker-compose.yml`»;
  - я так і зробив (через override, бо матеріали курсу не правлю);
  - `.github/workflows/eval-gate.yml` із того самого стартера цього не переживає.

  **Дві поради курсу з двох файлів одного репозиторію несумісні, і ніде про це не
  сказано.** Причому це не гіпотетично: у мене реально зайняті 8080 і 5432, тобто
  я — саме той студент, на якого розрахована порада, і саме він і ламає собі
  тиждень 6. Симптом при цьому максимально неінформативний: гейт «висить» 3.5 хвилини
  і падає на таймауті, а в логах сервіс пише, що все добре.

  Фікс, який я зробив: `docker-compose.override.yml` → у `.gitignore`, у репозиторії
  лежить `docker-compose.override.yml.example`. Правильний фікс на боці курсу — або
  згадати це в §8, або в шаблоні workflow не битися в хостовий порт (evals і так
  можуть ходити всередині docker-мережі, як радить §6 того самого гайду).

  І окремо на користь L11: блок 04 («CI ≠ ваш ноутбук») попереджає саме про цей клас
  проблем і виявився правий буквально. Я прогнав кроки workflow локально, отримав
  exit 1 → exit 0, був упевнений — і все одно впав на реальному CI з причини, якої
  локально не існує. «Гейт треба прогнати на реальному CI до того, як він комусь
  заблокує реліз» — найкорисніша порада тижня, і вона підтверджена на мені.
