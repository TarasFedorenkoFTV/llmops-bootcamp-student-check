# Starter repository

Те, що студент клонує на першому занятті й дороблює до capstone.

**➡ Повний гайд для студента (вимоги, запуск, кожна папка, troubleshooting): [GETTING_STARTED.md](GETTING_STARTED.md).**
**➡ Домашні завдання — окремий файл на кожен тиждень: [homework/](homework/README.md).**

## Що дається готовим, що добудовує студент

| Компонент | Дається готовим | Студент добудовує |
|---|---|---|
| UI (Angular) | готові в'юхи: Chat + Console/Observability | не змінює |
| App service (.NET) | skeleton | control plane: routing, fallback, cost, policies |
| Observability API (.NET) | skeleton | агрегати з Postgres (traces, p95, cost, error-taxonomy) у Console-в'юху |
| Gateway (LiteLLM) | базовий конфіг | моделі/провайдери, порядок fallback |
| Mock provider | готовий | використовує для тестів і failure-сценаріїв |
| Postgres | базова схема | розширює під logs / cost / prompt records |
| Eval runner (Python) | skeleton | dataset, graders, пороги |
| CI (GitHub Actions) | шаблон `.github/workflows/eval-gate.yml` | eval gate |
| Redis / дашборди | опційний шаблон | advanced extension |

## Запуск (мінімальний стек)

```sh
docker compose up --build
```

Піднімаються: UI (`:4200`), сервіс (`:8080`), LiteLLM (`:4000`), Postgres, mock provider.
Для mock реальні ключі не потрібні. Redis і дашборди — опційні: `docker compose --profile advanced up`.
Для оцінки якості (model-based evals): `cp gateway/.env.example gateway/.env` і заповнити ключі.

# Мої рішення по тижнях (студентські нотатки)

Детальний хід — у [student-journal.md](student-journal.md).

## Порт-мапінг (не як у курсі)

На хості зайняті `8080` (EDB PEM Apache) і `5432` (PostgreSQL 18), тому
`docker-compose.override.yml` мапить сервіс на **18080**, Postgres на **15432**.
Усі команди курсу, що бʼють по `localhost:8080`, у мене — `localhost:18080`.

## W2 — політика маршрутизації і fallback-порядок

Повернення, скарги і термінове → `mock-strong`; решта → `mock-mini`.
Причина: помилка «переплатили за просте» дешевша за «зекономили на скарзі».
Fallback-порядок: `mock-strong → mock-mini` (відповісти дешевшою краще, ніж не відповісти).

## W4 — керований інцидент, якого не дає стартер

Маркер `__fail_503` їде в тексті, тому кладе **обидва** елементи ланцюга — успішний
fallback на mock побачити нема як. Додав у `gateway/litellm-config.yaml` модель
`mock-dead` (`api_base: .../v1?fail=503` — збій вшитий в endpoint) і маркер `__outage`,
який ставить її першою в ланцюг. Тепер «основна впала, резерв відповів» перевіряється.

## W5 — поріг evals

**13 кейсів, поріг 12.** За правилом hw5: при N ≤ 10 поріг N−1, далі ≥ 85%.
13 × 0.85 = 11.05 → 12 (беремо строгіше з двох правил).
Запас 1 кейс покриває одиничний флейк і не паралізує релізи; регресія промпта валить
одразу 4 кейси (`faq-1`, `faq-2`, `caps-1`, `thanks-1`) і пробиває поріг гарантовано.
Safety страхую не порогом, а кількістю: 4 кейси на три родини injection — поломка
класу валить кілька кейсів разом.

## W5 — SLO і бюджет помилок (опційне)

**SLI:** частка звернень, на які система дала змістовну відповідь — тобто не заглушку
деградації і не відмову guardrail. Рахується з лога:
`status = '200' AND cache_hit IS NOT NULL AND blocked IS NULL`.

**SLO: ≥ 99%.** Обрано на те, що відчуває користувач, а не на uptime процесу:
сервіс може бути живий і роздавати «тимчасові проблеми».

**Бюджет помилок:** при 10 000 звернень на тиждень — 100 невдач. Поки бюджет не
витрачений, можна котити зміни; витратили за три дні — решту тижня займаємось
стабільністю. Це замінює суперечку «швидко чи надійно» на число.

## W5 — перевірка датасету на фальш-позитиви

`evals/golden.outage.jsonl` — копія набору з префіксом `__fail_503` у кожному `input`
(перевірка з hw5 п.4). Результат: **4/13 пройдено, не 0** — і це не дефект набору.
Зеленіють рівно 4 `expect_refusal`-кейси, бо мій injection-guardrail стоїть **на межі**,
до виклику моделі (як вимагає L08 блок 02), і відмовляє незалежно від здоров'я
провайдера. Це правильна поведінка: атаку треба відбити навіть тоді, коли модель лежить.
Критерій hw5 «0 пройдених» справедливий лише для стартера, де відмову віддає mock.
Лікування, яке пропонує hw5 (`forbid` із текстом заглушки), тут не застосовне:
у відповіді немає тексту заглушки — там справжня відмова.

## Команди відтворення

```bash
docker compose up --build -d
# прогріти стек (на холодному gateway перший виклик падає)
curl -s -X POST localhost:18080/chat -H "Content-Type: application/json" -d '{"message":"warmup"}'

# 1. НОРМА
curl -s -X POST localhost:18080/chat -H "Content-Type: application/json" -d '{"message":"warm up ok"}'
curl -s localhost:18080/observability

# 2. ІНЦИДЕНТ — 4 керовані збої
for i in 1 2 3 4; do curl -s -X POST localhost:18080/chat -H "Content-Type: application/json" -d '{"message":"__fail_503"}'; done
curl -s localhost:18080/observability
curl -s localhost:18080/providers

# 3. ВІДНОВЛЕННЯ — почекати ~6с (half-open) і спитати УНІКАЛЬНИМ текстом (не з кешу!)
sleep 6
curl -s -X POST localhost:18080/chat -H "Content-Type: application/json" -d '{"message":"probe unique-2026-08-04"}'
curl -s localhost:18080/providers
```

## Пастка, яку я знайшов і якої немає в матеріалах курсу

**Cache-hit маскує відновлення.** Якщо «переконатися, що відпустило» перевіряти
питанням, яке вже лежить у кеші, — відповідь прийде нормальна (0 мс), але виклику в
gateway не буде, тому circuit breaker не отримає пробного запиту, і `/providers`
показуватиме `down` **скільки завгодно довго**. Перевірено:

```
провайдери після "відновлення" питанням з кешу:  mock-mini · down (fails=3)
питання з унікальним текстом (реальний виклик):  [11ms] нормальна відповідь
провайдери після нього:                          mock-mini · ok (fails=0)
```

Наслідок операційний: плитка «Надійність провайдерів» бреше після інциденту так само,
як брехала б під час нього. Курс наполягає, що «плитка не має права зеленіти посеред
інциденту», але зворотний випадок — плитка не має права червоніти після нього — не
розглядає. Правильний фікс — health-проба провайдера **повз кеш** (окремий фоновий
probe), а не перевірка живим трафіком. У runbook я поки закрив це дисципліною:
перевіряй унікальним текстом.

# Постмортем цього інциденту

- **Що зробимо, щоб не повторилося:** інцидент навчальний і симульований, тому
  «не повториться» тут не про провайдера, а про мій контур. Реальна знахідка —
  маскування відновлення кешем (вище). Механізм-відповідь: фоновий health-probe
  провайдера, який не проходить через кеш.
- **Як ми дізналися:** з консолі (`error_rate_pct` 0 → 22.2, `fallback_events` 0 → 3,
  `/providers` → down), а не зі скарг. Діри в спостережуваності немає.

# KPI-мова: що кожна плитка означає для бізнесу (лаба L12 крок 3)

| Плитка / механізм | Мовою тих, хто вирішує про бюджет | Артефакт-доказ |
|---|---|---|
| FALLBACK + graceful degradation | падіння провайдера користувач не помічає — жодної 500-ки за весь інцидент | таймлайн вище |
| CACHE-HIT | частина запитів безкоштовна і миттєва (0 мс, 0 токенів) | `cache_hit` у лозі |
| routing mini/strong | дорога модель дістається тільки складним задачам; вартість запиту керована | ескалація $0.000142 проти FAQ $0.000016 — 9× |
| ВАРТІСТЬ / бюджет | витрати видно сьогодні, а не в рахунку через місяць | `GET /cost` |
| eval-гейт у CI | регресія якості фізично не потрапляє в main | 8/13 → exit 1; 13/13 → exit 0 |
| Approvals · HITL | жодна незворотна дія не виконується без людини; є журнал відхилених | черга + `reject` |
| P95 / ERROR RATE | видно те, що бачать найневдаліші користувачі, а не «середня по лікарні» | `GET /observability` |
| Prompt registry | відкат зміни поведінки — секунди, без деплою, зі слідом у лозі | `POST /prompts/{v}/activate` |

Формулювання «3 хвилини для людини без інженерного бекграунду»:
> LLM-фіча без контуру керування — це некерована вартість, крихкість і сліпота.
> Ми закрили три речі: падіння провайдера користувач не помічає; регресія якості
> фізично не мержиться; жодна незворотна дія не робиться без людини. Ось консоль —
> усе це на одному екрані, у реальному часі.

# 30-day rollout: як принести це у свою команду (hw6 п.4)

Порядок не випадковий: кожен шар потребує даних попереднього, і перший тиждень
самоокупний.

1. **Тиждень 1 — unified log + вартість.** Один рядок на запит (`request_id`, модель,
   версія промпта, токени, `cost_usd`, статус, латентність) і розрахунок вартості з
   `usage` у момент відповіді.
   *Готово, коли:* будь-яке питання про гроші закривається одним SQL-запитом, а не
   рахунком провайдера наприкінці місяця.
2. **Тиждень 2 — реєстр промптів.** Промпти з коду в таблицю з версіями; активна
   версія читається на кожен запит; `prompt_version` їде в лог; promote/rollback —
   один атомарний `UPDATE`.
   *Готово, коли:* відкат промпта займає секунди і лишає слід, а «яка версія
   відповідала користувачу в 19:42» — це SELECT.
3. **Тиждень 3 — evals на критичні сценарії.** 10–15 кейсів на те, що страшно зламати:
   топ реальних інтентів із лога плюс сценарії, поломка яких найдорожча (дії, атаки,
   ескалації). Обов'язково перевірити на фальш-позитиви — прогін при повністю
   зламаному провайдері.
   *Готово, коли:* навмисно зламаний промпт робить прогін червоним відтворювано.
4. **Тиждень 4 — гейт у CI.** Exit code вже є з тижня 3 — лишається повісити його на
   PR і **увімкнути required status check** на захищеній гілці (без цього кроку гейт
   лише «радить»). Плюс дешеві статичні перевірки поруч: прайс покриває всі моделі
   з конфіга, схеми валідні, у діфі немає секретів.
   *Готово, коли:* червоний прогін блокує merge, і в історії CI є доказ — червоний,
   фікс, зелений.

**Чого НЕ робити в перший місяць:** semantic cache, LLM-as-judge, canary, окремий стек
метрик. Кожне з них додається під **виміряну** проблему; якщо не можеш назвати
метрику, яка після впровадження мусить змінитися, — механізм ще не потрібен.
Єдиний виняток, який робиться відразу і без сигналу: черга підтверджень у базі
(а не в пам'яті), відсутність секретів у коді, ліміт витрат у кабінеті провайдера —
бо сигналом тут буде вже наслідок.
