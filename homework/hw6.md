# HW6 (після L11–L12): CI-гейт + інцидент

Мета тижня: зміни промпта/моделі виходять як контрольований реліз, а інцидент має
відпрацьований сценарій. Це фінал — система зібрана.

> **Навіщо це в реальній системі.** Гейт цінний рівно настільки, наскільки він
> здатний бути червоним. У пайплайні одного сервісу довго жила обгортка, що
> «м'якшила» quality gate: крок виконувався, а його негативний результат не
> валив збірку — зелений колір був, захисту не було; прибирали як баг. Тому
> перевірка вашого гейта — не «крок є», а «зламав навмисно → merge заблокований».
> І друге: автоматика, що робить незворотне, виходить першим релізом у режимі
> dry-run — проходить повний цикл і пише звіт «що я б зробила»; запобіжник
> знімають після кількох днів читання звітів.

## Обов'язково

1. Вмикає eval-гейт у CI свого репозиторію (шаблон `.github/workflows/eval-gate.yml`
   уже є): на PR стек піднімається, evals блокують merge при регресії; поріг — під
   свій датасет із HW5.
2. Демонструє гейт: PR зі зламаним промптом → CI червоний; виправлення → зелений.
   Обидва прогони мають лишитися в історії Actions. Як це виглядає — живий приклад:
   [demo-PR в еталонному репозиторії](https://github.com/TarasFedorenkoFTV/llmops-bootcamp-solutions/pull/1)
   (червоний прогін → фікс → зелений, PR закритий без мержа).
3. Пише в README свого репо інцидент-демо: сценарій «інцидент → fallback →
   відновлення» і команди для відтворення. «Відновлення» для core-доріжки — це:
   після серії збоїв звичайне питання знову відповідає нормально, а консоль
   показує сплеск і спад fallback (half-open — лише якщо робив опційний CB).
4. README-розділ «30-day rollout»: чотири кроки перенесення практик курсу у СВОЮ
   команду (по одному реченню на крок) — головний transfer-артефакт курсу.
   Начерк уже є з лаби L12 — доведи його до чотирьох чітких кроків.

## Опційно (не оцінюється)

- Canary-план: як роутером розділити трафік 90/10 між двома версіями промпта і за
  якими метриками вирішувати promote/rollback.
- `/metrics` + зовнішній дашборд поверх advanced-профілю.

## Що здає

Фінальний PR: система збирається `docker compose up`, всі плитки консолі живі,
CI-гейт працює (є червоний і зелений прогін в історії), README з інцидент-демо.

## Що перевіряє ментор

| Перевірка | Як | Очікується |
|---|---|---|
| Гейт існує | вкладка Actions у репо студента | прогони eval-gate на PR |
| Гейт ловить | історія CI | є червоний прогін (регресія) і зелений (фікс) |
| Інцидент-демо | виконати команди з README студента | fallback і відновлення відтворюються |
| Фінальна збірка | `docker compose up --build` з чистого клону | система працює, консоль жива |
| Поріг гейта | значення `--threshold` у workflow + пояснення в README | не нижче за правило з HW5 (N−1 при N≤10, далі ≥85%); занижений без обґрунтування — на доопрацювання |
| 30-day rollout | README | 4 кроки, конкретні, прив'язані до практик курсу |

## Самоперевірка перед здачею

Клонуй свій репозиторій у чисту папку і зроби `docker compose up --build`. Якщо щось
не піднялося або консоль порожня — ментор побачить те саме.

**Якщо гейт червоний з незрозумілої причини** — три відомі граблі з L11:
(1) цикл очікування без `if curl; then` вбивається `bash -e`; (2) холодний
gateway 500-ить перший запит — потрібен окремий wait-крок; (3) перевірка
успіху «код == 200» замість діапазону. Time-box: понад 1.5 год дебагу — здай
лог червоного прогону з гіпотезою і добий після рев'ю ментора.
