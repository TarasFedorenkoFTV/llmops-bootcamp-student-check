# HW6 (після L11–L12): CI-гейт + інцидент

Мета тижня: зміни промпта/моделі виходять як контрольований реліз, а інцидент має
відпрацьований сценарій. Це фінал — система зібрана.

> **Навіщо це в реальній системі.** Гейт цінний рівно настільки, наскільки він
> здатний бути червоним. У пайплайні одного сервісу довго жила обгортка, що
> «м'якшила» quality gate: крок виконувався, а його негативний результат не
> валив збірку — зелений колір був, захисту не було; прибирали як баг. Тому
> перевірка вашого гейта — не «крок є», а «зламав навмисно → merge заблокований».
> І друге: автоматика, що робить незворотне, виходить першим релізом у режимі
> dry-run — проходить повний цикл і пише звіт «що я б зробила»; запобіжник
> знімають після кількох днів читання звітів.

## Обов'язково

1. Вмикає eval-гейт у CI свого репозиторію (шаблон `.github/workflows/eval-gate.yml`
   уже є): на PR стек піднімається, evals блокують merge при регресії; поріг — під
   свій датасет із HW5. Щоб чек справді **блокував** merge, увімкни required
   status check: Settings → Branches → Add branch protection rule → Require
   status checks to pass → `eval-gate`. На приватному репо безкоштовного плану
   branch protection може бути недоступний — чесно зазнач це в описі PR;
   гейт тоді «радить», а не блокує.
2. Демонструє гейт: PR зі зламаним промптом → CI червоний; виправлення → зелений.
   Обидва прогони мають лишитися в історії Actions. Як це виглядає — живий приклад:
   [demo-PR в еталонному репозиторії](https://github.com/TarasFedorenkoFTV/llmops-bootcamp-solutions/pull/1)
   (червоний прогін → фікс → зелений, PR закритий без мержа).

   > **План Б: GitHub Actions недоступний** (корпоративна політика, GHE без
   > Actions). Мінімально приймальний замінник: прожени кроки workflow локально
   > руками — підняти стек → evals → перевірити exit code — і додай у PR чесну
   > позначку «CI не запускався: Actions недоступні» разом із виводом прогону.
   > Це неповне закриття тижня, і це варто розуміти прямо: гейт у такому режимі
   > «радить», а не «вирішує» — merge нічим не блокується.

3. Пише інцидент-демо в окремому `INCIDENT_RUNBOOK.md` у корені свого репозиторію
   і дає на нього посилання з README (так це влаштовано на уроці 12): сценарій
   «інцидент → fallback → відновлення» і команди для відтворення — виконувані
   **дослівно**, з реальним хостом, без `...`-заглушок. «Відновлення» для
   core-доріжки — це: після серії збоїв звичайне питання знову відповідає
   нормально, а консоль показує сплеск `fallback_events` і спад `error_rate_pct`
   (`fallback_events` — кумулятивний лічильник, він не спадає ніколи, тож спад
   показує саме error rate). Контрольне питання на кроці відновлення — **нове**,
   якого ще не було в кеші: інакше демо зазеленіє посеред інциденту, бо кеш
   віддасть стару відповідь із `latency_ms=0` (half-open — лише якщо робив
   опційний CB).
4. README-розділ «30-day rollout»: чотири кроки перенесення практик курсу у СВОЮ
   команду (по одному реченню на крок) — головний transfer-артефакт курсу.
   Начерк уже є з лаби L12 — доведи його до чотирьох чітких кроків.

## Опційно (не оцінюється)

- Canary-план: як роутером розділити трафік 90/10 між двома версіями промпта і за
  якими метриками вирішувати promote/rollback.
- `/metrics` + зовнішній дашборд поверх advanced-профілю.

## Що здає

Фінальний PR: система збирається `docker compose up`, всі плитки консолі живі,
CI-гейт працює (є червоний і зелений прогін в історії), `INCIDENT_RUNBOOK.md`
з інцидент-демо (+ посилання з README).

## Що перевіряє ментор

| Перевірка | Як | Очікується |
|---|---|---|
| Гейт існує | вкладка Actions у репо студента | прогони eval-gate на PR |
| Гейт ловить | історія CI | є червоний прогін (регресія) і зелений (фікс) |
| Гейт живий на поданому стані | у PR зламати промпт одним комітом (activate v1 у міграції або окремий demo-PR) → потім revert; плюс `grep -n "continue-on-error" .github/workflows/eval-gate.yml` | **червоний обов'язковий чек, який блокує merge**, після revert — зелений; grep дає нуль влучань у кроці Evals. Історія Actions тритижневої давнини цей рядок **не** закриває — перевіряється поточний стан гейта |
| Інцидент-демо | виконати команди з `INCIDENT_RUNBOOK.md` студента (посилання з README) | fallback і відновлення відтворюються; команди виконувані дослівно; питання на кроці відновлення — нове, не з кешу |
| Фінальна збірка | `docker compose up --build` з чистого клону | система працює, консоль жива. Якщо на машині зайняті стандартні порти — піднімайся з файлом зсунутих портів: `docker compose -f docker-compose.yml -f demo-ports.yml up --build -d` (файл лежить у стартері); це не порушення «однієї команди» |
| Поріг гейта | значення `--threshold` у workflow + пояснення в README | оновлений у **двох** місцях — локальна команда і workflow; не нижче за правило з HW5 (N−1 при N≤10; при N>10 — `ceil(0.85·N)`, 85% з округленням угору); занижений без обґрунтування — на доопрацювання |
| 30-day rollout | README | 4 кроки, конкретні, прив'язані до практик курсу |

## Самоперевірка перед здачею

Клонуй свій репозиторій у чисту папку і зроби `docker compose up --build`. Якщо щось
не піднялося або консоль порожня — ментор побачить те саме.

**Якщо гейт червоний з незрозумілої причини** — три відомі граблі з L11:
(1) цикл очікування без `if curl; then` вбивається `bash -e`; (2) холодний
gateway 500-ить перший запит — потрібен окремий wait-крок; (3) перевірка
успіху «код == 200» замість діапазону. Time-box: понад 1.5 год дебагу — здай
лог червоного прогону з гіпотезою і добий після рев'ю ментора.
